# React 19 SSR UI Architecture Migration

> Triage label: `ready-for-agent`

## Problem Statement

The server-rendered UI for both the zero-login shop-floor Worker Portal and the authenticated Department Heads `/fleet` PWA is currently built with manual HTML string concatenation, template literals, and explicit `escapeHtml` calls across many modules, with some HTML view builders still living directly inside Fastify route handlers and mixing markup, TypeScript interfaces, CSS stylesheets, and inline client scripts. As features expand—such as the 44-unit workshop schematic, Urgency Triage board, firmware OTA rollout controls, and versioned presets—maintaining raw HTML strings increases engineering cost, makes component reuse brittle, risks accidental unescaped dynamic content or malformed attributes, and forces developers to navigate tangled markup, types, and styles in the same files.

## Solution

Rebuild the Fastify-served UI layer using typed React 19 Server-Side Rendering (`react-dom/server` TSX components) compiled directly under the existing TypeScript `NodeNext` build without introducing a client-side bundler. Enforce a strict, consistent file-separation convention across every UI module—`<name>.tsx` for React JSX views, `<name>.types.ts` for TypeScript props, interfaces, and view-models, `<name>.styles.ts` for CSS stylesheets, and `<name>.client.ts` for progressive-enhancement browser scripts where needed—so future layout, styling, and contract updates stay isolated, type-checked, and low-cost while preserving zero-CDN delivery, zero-JS Worker Portal pages, and 100% compatibility with existing workflows, DOM hooks, and API contracts.

## Implementation Decisions

- **React 19 SSR Toolchain:** Add React 19 and React DOM server rendering packages alongside their TypeScript type definitions, and enable TypeScript `react-jsx` compilation under `NodeNext`. The standard TypeScript build and container image compile server TSX views directly with zero Vite, Webpack, or esbuild client-bundler pipeline.
- **Consistent Module File Separation (`<name>.tsx`, `<name>.types.ts`, `<name>.styles.ts`, `<name>.client.ts`):** Every UI feature module strictly separates responsibilities into consistent companion files: `<name>.tsx` holds React functional components and compatibility render wrappers, `<name>.types.ts` holds exported props, state, and view-model TypeScript interfaces, `<name>.styles.ts` holds scoped `@layer` CSS stylesheets, and `<name>.client.ts` holds any progressive-enhancement browser runtime script for that feature. Shared layout tokens and base portal styles remain centralized in dedicated style modules rather than inline strings inside routes or TSX components.
- **Thin Route Boundary & Backward-Compatible Exports:** Fastify HTML route modules for the Worker Portal directory and machine landing, Worker Glossary, Worker Bug Report, Department Heads `/fleet` PWA, and Cloudflare Access HTML error fallback only fetch domain data, validate input, and pass typed view-models into UI view modules. All existing public `render*` function signatures and type exports are preserved (via wrapper functions or route re-exports where needed) so existing callers and test suites remain unbroken.
- **Central SSR Rendering & HTML5 Attribute Fidelity:** A dedicated SSR helper module wraps `renderToStaticMarkup`, prepends the HTML5 doctype for full-document responses, normalizes single-quote entities for strict compatibility with existing XSS assertions, preserves non-color status symbols and shop-floor labels, and guarantees exact HTML serialization of modern HTML5 attributes that React's standard serializer would otherwise alter (`closedby="any"`, `hidden="until-found"`, `focusgroup="tablist nomemory"`, boolean `focusgroupstart`, and `popover="auto"`).
- **Zero-JS Worker Portal & Pure React Markdown:** Worker Portal machine directory, machine landing, glossary, unknown-machine recovery, and bug-report confirmation views emit zero `<script>` tags. Troubleshooting `fix_steps_md` content parses directly into React `<ol>`, `<ul>`, `<p>`, and `<code>` elements using React's native text escaping instead of `dangerouslySetInnerHTML` or raw HTML string injection.
- **Fleet PWA Interactive Progressive Enhancement:** All `/fleet` server-rendered markup—the header and live polling controls, KPI summary strip, ESP32 winding cycle card, 4-tab shell, repeat-fault strip, triage toolbar and 3-tier Urgency Triage board, 44-unit L-shaped workshop blueprint and overflow reserve bay, batch OTA/preset toolbar, Firmware & Presets management tab, native `<dialog>` drawer, and glossary popover—is rebuilt as composable React TSX components while keeping all existing DOM IDs, `data-*` attributes, XSS-escaped JSON bootstrap script payload, and modular `<name>.client.ts` progressive-enhancement scripts intact.
- **File Size & Domain Invariants:** Keep every module concise and under 700 lines, preserve zero-CDN asset delivery, keep mobile touch-target (`>= 48px` / `52px` coarse) and `forced-colors` CSS guarantees, and never expose legacy zone labels (`NORTH_LEFT`, `NORTH_RIGHT`, `MAIN_BANK`, `EAST_DOOR`) or Fleet OTA/preset controls on Worker Portal screens.

## Testing Decisions

- **Primary Seam (Existing Highest Seam):** Exercise the Fastify application factory composition seam (`createApp` wired to real PostgreSQL/TimescaleDB and the in-memory MQTT transport) via HTTP injection across all public Worker Portal routes, authenticated `/fleet` PWA routes, and Cloudflare Access HTML auth fallback states.
- **Secondary Seam (Direct SSR UI Seam):** Test React UI components and preserved `render*` helpers directly via JSX rendering to verify automatic XSS escaping in text and attributes, pure React Markdown rendering, non-color status cues, and exact HTML5 attribute output (`closedby="any"`, `hidden="until-found"`, `focusgroup`, `focusgroupstart`, `popover="auto"`).
- **What Makes a Good Test:** Assert only observable external outputs—HTTP status codes, content-type headers, semantic landmark/heading hierarchy, ARIA and HTML5 attributes, escaped XSS payloads, zero-CDN and zero-script guarantees, and accurate machine/telemetry/OTA state—never internal React component tree implementation details.
- **Prior Art:** Follow the established Vitest real-DB integration suites covering the Worker Portal shell, inline recent errors, Worker Glossary, Report-a-Bug form and confirmation, Department Heads `/fleet` PWA, floor-position decoupling, and Cloudflare Access authentication.

## Out of Scope

- Introducing client-side build tools or bundlers (Vite, Webpack, esbuild) or converting the Worker Portal into a client-side SPA.
- Rewriting `/fleet`'s progressive-enhancement client DOM scripts into a client-hydrated React bundle (`hydrateRoot`).
- Modifying PostgreSQL/TimescaleDB schemas, MQTT ingestion contracts, JSON REST API payloads, Cloudflare Access JWT validation logic, Grafana dashboards, or ESP32 C++ firmware.
- Visual redesigns or functional changes to existing shop-floor operator or department-head workflows.

## Further Notes

- Replacing `/fleet`'s progressive-enhancement client scripts with client-side React hydration can be evaluated as an independent follow-up once the React 19 SSR component and `<name>.tsx` / `<name>.types.ts` / `<name>.styles.ts` / `<name>.client.ts` structure is in place.
- Repository documentation should be updated alongside implementation to describe the React 19 SSR layer and consistent module file naming convention.
